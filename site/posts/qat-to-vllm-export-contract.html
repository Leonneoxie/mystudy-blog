低精度部署

从 QAT 到 vLLM：量化模型真正可部署需要哪些契约

解释为什么训练阶段的 fake quant 和 QuantLinear 不能直接视为部署产物，并给出 Quant IR、标准格式 lowering、权重打包和真实 kernel 验收的完整链路。

QAT 结果必须经过可验证的导出契约

TECH MAP
01Fake Quant
02Quant IR
03Weight Pack
04vLLM Kernel
  • 训练 wrapper 不是部署格式
  • 数值语义与物理布局分离
  • 加载成功不等于量化生效

最容易产生的误解

模型完成 QAT，验证集精度也不错，于是把 checkpoint 保存下来，就认为“量化模型已经可以部署”。

实际上，训练框架中的量化模型通常包含：

  • fake-quant 节点；
  • STE 舍入；
  • 可学习 scale、clip 或 zero-point；
  • QuantLinear、proxy、wrapper；
  • 用浮点张量模拟的整数范围；
  • 训练专用状态和 observer。

而 vLLM 消费的是另一套契约：

  • 它认识的量化配置；
  • 指定名称的 packed tensors；
  • 固定的 axis、group size、zero-point 约定；
  • tensor-parallel 下的切分布局；
  • 能匹配这些布局的真实 kernel。

两者之间必须存在明确的 finalize、Quant IR、lowering 和 packing。

训练模型、数学语义和物理格式必须分层

推荐分为四层：

QAT Training Graph
      ↓ freeze / finalize
Canonical Quant IR
      ↓ target capability + lowering
Standard Checkpoint Format
      ↓ runtime dispatch
vLLM Quantized Kernel

QAT Training Graph

负责让梯度穿过量化操作，可以使用 wrapper、proxy 和浮点模拟。它的模块结构服务于训练，不应成为部署 API。

Canonical Quant IR

保存后端无关的数学语义：

QuantSpec(
    dtype="int",
    bit_width=4,
    symmetric=True,
    granularity="group",
    group_size=128,
    axis=0,
    scale=...,
    zero_point=None,
    rounding="nearest",
)

IR 必须区分 logical quantization 与 storage layout。INT4 数学值不等于磁盘中 nibble 的具体排列。

Standard Checkpoint Format

例如 compressed-tensors、GPTQ 或 AWQ。它定义：

  • config.json 中的量化字段；
  • tensor 名称；
  • packing 顺序；
  • scale/qzero/g_idx 的 shape 和 dtype；
  • ignored layers；
  • fused QKV/MoE 的映射。

Runtime Kernel

最终决定量化有没有产生实际收益。加载成功但先反量化成 FP16 GEMM，只能证明兼容，不能证明加速。

为什么推荐先导出标准格式

如果 AMCT 或其他量化工具直接实现 quant_amct 自定义 vLLM 插件，就要长期维护：

  • vLLM QuantizationConfig；
  • Linear/MoE method；
  • 权重加载器；
  • CUDA/NPU kernel；
  • tensor parallel；
  • fused QKV；
  • vLLM 版本适配。

如果量化语义可以映射到 compressed-tensors、GPTQ、AWQ 或 FP8，优先输出标准格式能够复用 vLLM 已有 loader 和 kernel。

自定义插件应当是“标准格式确实无法表达”的结果，而不是为了省掉 converter 设计。

compressed-tensors lowering 需要做什么

以 W4A16 group-128 为例，lowering 至少完成：

配置转换只是其中一半，另一半是权重 packing。

权重 packing 为什么容易错

一个形状为 [out_features, in_features] 的 INT4 权重，落盘时可能发生：

  • 两个 4-bit 值打进一个 byte；
  • 32-bit word 内部重新排序；
  • K/N 轴转置；
  • group padding；
  • tensor-parallel 分片后再 pack；
  • scale 被 reshape 或重排。

因此 packer 必须提供测试用 unpack()：

packed = pack(qweight, spec)
restored = unpack(packed, spec)
assert torch.equal(restored, qweight)

至少覆盖负数、极值、奇数长度、padding、group 边界和多 shard。

模型名称映射是另一个高风险区

Hugging Face Qwen 中可能是：

model.layers.0.self_attn.q_proj.weight
model.layers.0.self_attn.k_proj.weight
model.layers.0.self_attn.v_proj.weight

vLLM 运行时可能把它们加载进融合 QKV 模块。类似地，gate_proj 和 up_proj 可能进入 merged column-parallel layer。

需要显式维护：

HF parameter name
↕
Canonical Quant IR name
↕
vLLM fused/parallel parameter name

不能依赖字符串替换碰运气。

四级 Oracle

建议建立：

O0：浮点模型
O1：QAT fake-quant 模型
O2：finalized Quant IR reference executor
O3：vLLM 导出模型

比较关系：

  • O0 ↔ O1：量化算法造成多少质量损失；
  • O1 ↔ O2：freeze/finalize 是否改变语义；
  • O2 ↔ O3：导出、packing 和 kernel 是否正确。

如果只比较 O0 和 O3，出现误差时无法判断问题来自训练还是导出。

“vLLM 能加载”为什么不是完成

完整验收至少包括：

  1. 未安装量化工具插件的标准 vLLM 能加载；
  2. 日志识别到预期 quantization scheme；
  3. profiler 证明运行目标量化 kernel；
  4. O2/O3 logits 在合理容差内；
  5. PPL 退化符合算法预期；
  6. 显存或吞吐产生量化收益；
  7. tensor parallel 场景没有 shape/name 错误。

还需要主动测试失败场景：

  • 不支持的 group size；
  • scale shape 不匹配；
  • checkpoint 缺 shard；
  • 配置写 W4、权重实际还是 FP16；
  • Hadamard transform 没有 fold；
  • vLLM 版本超出验证范围。

正确行为是明确失败，而不是静默回退。

QAT 中什么应该学习

Brevitas 值得借鉴的 QAT 能力包括：

  • stats/MSE 初始化后切换为可学习 scale；
  • 可学习 clipping；
  • learned rounding；
  • quantization metadata 传播；
  • prepare/calibrate/train/finalize/export 生命周期；
  • exporter manager 与训练图解耦。

对于大模型，建议升级路径：

PTQ
→ Learned Round / block reconstruction
→ LoRA + scale/clip QAT
→ Partial QAT
→ Full QAT

不是所有 W4 问题都值得上 full QAT。先判断损失来自权重离群值、激活动态范围、敏感层还是部署格式不匹配。

一个可落地的完成定义

以 Qwen3 W4A16 group-128 为例：

QAT/PTQ 只运行一次
→ 生成 Canonical Quant IR
→ 导出 compressed-tensors
→ 标准 vLLM 无插件加载
→ O2/O3 对拍
→ 确认真实 W4 kernel
→ 记录 PPL、显存、prefill/decode 吞吐

达到这一步，才能说“量化模型已经从算法实验走到部署资产”。

以 Qwen3 小模型为例的适配清单

接入前先生成模块清单，不要直接全局替换 nn.Linear：

for name, module in model.named_modules():
    if isinstance(module, torch.nn.Linear):
        print(name, module.in_features, module.out_features)

再按语义分类 q/k/v/o_proj、gate/up/down_proj、embedding、lm_head 与共享权重。每类明确量化轴、group size、排除规则、旋转策略和导出名称。Qwen3 的 GQA、RoPE、门控 MLP 与 tied embedding 都会影响映射，不能只凭类名替换。

阶段最小产物失败即停止
浮点基线logits、困惑度/任务分数基线不可复现
Fake quantscale 与敏感层报告NaN 或质量断崖
QATloss、梯度、冻结策略训练图语义不清

checkpointconfig、packed weights、映射独立 reader 失败
vLLMloader + 对应 kernel静默反量化
Serving质量、TTFT、TPOT、显存仅能加载但无收益

Hadamard 与旋转量化如何判断是否适合

Hadamard/正交旋转把离群值能量摊到更多通道，使低比特误差更均匀。它不是一个随意打开的布尔开关：必须证明旋转能吸收到相邻权重，或由 runtime 的在线旋转 kernel 消费。

应做四组消融：普通 PTQ、校准/平滑、离线可吸收旋转、在线旋转。固定 calibration 数据和评测集，比较层级 SQNR、最终质量、模型大小、加载时间与 TTFT/TPOT。若质量改善被在线旋转成本抵消，或 runtime 没有相应 kernel，该方案在当前部署目标下就不适合。

Wrapper、替换 Linear 与侵入式修改

  • Wrapper/graph transform 适合实验和 QAT：不改模型源码，按规则插入 fake quant；
  • 替换 Linear 适合原型，但必须处理共享权重、state dict 和非标准模块；
  • 修改模型源码 仅在语义无法由图变换表达时采用，维护成本最高；
  • Export lowering 应独立于训练 wrapper，经 Canonical Quant IR 落到 vLLM 格式。

Brevitas 值得借鉴的是模块化 quantizer、图变换、export manager 和后端契约分层，而不只是 QuantLinear。AMCT 若要同时支持自有 runtime 与 vLLM，应共享规范化 Quant IR，再分别实现 backend lowering，避免两个导出器各自解释训练图。

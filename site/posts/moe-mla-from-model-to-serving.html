为什么把 MoE 和 MLA 放在一起

它们解决不同问题：MoE 用稀疏激活扩大模型容量，MLA 压缩注意力的 KV 表示。但二者都会把模型创新转化为推理系统约束：前者引入路由与跨卡通信，后者改变缓存布局和 Attention kernel。

1. MoE 的基本计算

对 token 表示 x，router 产生专家分数并选 top-k：

$$y=\sum_{i\in TopK(g(x))}p_iE_i(x)$$

总参数可以很大，但每个 token 只激活少数专家。不能把“总参数少参与计算”直接等同于“推理一定便宜”：专家权重仍要存放，token dispatch 和 combine 需要通信。

2. Router 的四个工程问题

问题现象对策
负载不均少数专家过热auxiliary loss、bias 或容量控制
容量溢出token 被丢弃/转移capacity factor、动态路由
All-to-All通信压过计算expert parallel、拓扑感知
小 batch每个专家 token 太少聚合请求、融合 dispatch/GEMM

离线 benchmark 中均匀的 token 分布不能代表线上真实 prompt。应记录每层专家直方图、最大/平均负载比和通信占比。

3. MLA 为什么影响 KV Cache

传统 MHA 保存每个 KV head 的完整 K/V。MLA 将 K/V 投影到低维 latent 表示，推理时缓存 latent，并在计算路径中恢复需要的信息。收益来自更小缓存与更低读取量，代价是额外投影、特殊 RoPE 分解和定制 kernel。

关键验收不是“checkpoint 中 latent 维度更小”，而是 runtime 是否真的缓存压缩表示。如果加载器先展开成普通 K/V，算法收益就消失了。

5. 最小实践

先写 CPU router 模拟器，生成偏斜与均匀 token 分布，验证 dispatch/combine 后顺序不变；再用小矩阵实现 top-k expert MLP，与 dense oracle 对拍。MLA 则先验证完整 MHA 与“压缩→恢复”数学路径，再实现缓存格式。

6. Serving 验收

  • 分别测 prefill 与 decode；
  • 扫描并发和 token 分布，而不只测一个 batch；
  • 报告专家负载、All-to-All 时间、KV bytes/token；
  • 确认请求取消和抢占不会泄漏专家/KV 状态；
  • 与 dense/MHA baseline 比较质量、延迟、吞吐和显存。

Paged KV Cache 解决的不是注意力计算，而是显存管理

从连续预留的碎片问题出发，解释 block table、物理块分配、引用计数和分页注意力之间的契约。

问题背景

自回归生成需要保存每层注意力的 Key 和 Value。最直观的实现是为每个请求预留 max_seq_len 对应的连续空间，但真实请求长度差异很大：短请求浪费尾部空间，长请求又可能因为找不到足够大的连续区域而失败。

一句话结论

Paged KV Cache 把“序列逻辑位置”和“显存物理位置”分开：序列看到连续 token，内核通过 block table 找到离散物理块。它首先是一种内存管理设计，PagedAttention 是消费这种布局的执行内核。

三个核心对象

Sequence:    token 0 1 2 3 4 5 6
Logical:     block 0       block 1
Block table: [physical 7, physical 2]
Allocator:   free=[0,1,3,4,5,6,...]
  • 逻辑块：请求内部的连续编号。
  • 物理块：真实 KV Cache 存储单元。
  • block table：逻辑块到物理块的映射。

注意力 kernel 不能只收到一个连续 KV 指针，还必须收到 block table、每个序列的有效长度和块大小。这就是调度器、缓存管理器和 kernel 之间的元数据契约。

最小分配模拟

下面代码是 CPU 状态机模拟，不是 GPU PagedAttention 实测：

class BlockPool:
    def __init__(self, count):
        self.free = list(range(count))
        self.refs = [0] * count

    def alloc(self):
        if not self.free:
            raise RuntimeError("KV blocks exhausted")
        block = self.free.pop()
        self.refs[block] = 1
        return block

    def release(self, block):
        self.refs[block] -= 1
        if self.refs[block] == 0:
            self.free.append(block)

真实实现还需要处理共享前缀、copy-on-write、异常回滚和并发安全。引用计数错误通常不会立刻报错，而会表现为缓存泄漏或不同请求互相污染。

块大小不是越小越好

小块减少尾部碎片，但 block table 更长、元数据访问更多；大块降低映射开销，却增加请求最后一块的浪费。合理块大小取决于序列长度分布、kernel 支持和硬件访存特征，不能只看单请求峰值显存。

验收方法

  1. 随机生成不同长度请求，核对已用块与理论值。
  2. 完成和取消请求后，空闲块数量必须恢复。
  3. 共享前缀释放一个请求时，公共块不能提前回收。
  4. 物理块顺序打乱后，输出仍应与连续 KV 参考实现一致。

本篇提供原理和模拟验证；真实收益必须在固定模型、块大小、并发分布和 GPU 上报告。

Block table 如何进入 Attention

逻辑 token t 先定位逻辑块，再由 block table 找到物理块：

logical_block = token_pos // block_size
offset = token_pos % block_size
physical_block = block_table[request_id, logical_block]
kv_slot = physical_block * block_size + offset

Paged Attention kernel 必须按这层间接寻址读取 K/V。只实现分配器、却仍把 KV 拼成连续 tensor，并没有完成分页执行。

操作必须保持的不变量
allocatefree + allocated = total
appendtoken 逻辑顺序可恢复
fork/share引用增加但不复制物理块
release引用归零才回收
cancel/error重复清理不会 double free

推荐用随机状态机连续执行 allocate/append/fork/release，并在每一步检查不变量，比少量 happy case 更容易发现泄漏。

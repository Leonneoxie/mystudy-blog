问题背景

调用一个大模型服务时，我们通常只看到输入文本和逐步出现的输出 token。但在服务内部，请求需要经过分词、准入、批处理、KV Cache 分配、Prefill、Decode、采样和流式返回。任何一个阶段处理不当，都可能表现为首 token 慢、吞吐下降、显存浪费或尾延迟抖动。

如果只把推理理解成一次 model.forward()，就很难解释现代框架为什么需要调度器、分页 KV Cache、连续批处理和前缀缓存。

一句话结论

现代 LLM 推理引擎不是单纯的模型执行器，而是一套围绕“请求状态、显存块和每轮 token 预算”不断做资源决策的在线系统。

完整请求链路

一次典型请求可以抽象为：

HTTP / API 请求
    → 参数校验与分词
    → 准入队列
    → 调度器选择本轮序列
    → KV Cache 分配
    → Prefill 计算提示词
    → Decode 每轮生成一个或多个 token
    → 采样与停止条件
    → 流式返回并释放资源

这条链路中有三类状态同时变化：

  • 请求状态：等待、运行、抢占、完成或失败。
  • 模型状态：本轮输入 token、位置编码和注意力元数据。
  • 系统状态：可用显存块、批次 token 数、队列长度和流式连接。

Prefill 和 Decode 为什么必须区分

Prefill 一次处理提示词中的大量 token，通常能形成较大的矩阵乘法，计算密度较高。Decode 通常每个序列每轮只增加一个 token，却需要持续读取历史 KV Cache，更容易受到显存带宽和调度开销影响。

因此，两个阶段对资源的偏好不同：

阶段输入形态主要压力用户感知指标
Prefill一个请求的多个 token计算量、临时激活、准入预算TTFT，首 token 延迟
Decode多个请求各自的新 tokenKV Cache 读取、调度、同步TPOT，逐 token 延迟

如果无限制地接收长提示词，Prefill 会占据计算资源，让正在 Decode 的请求长时间等不到下一轮；如果只照顾 Decode，新请求又会一直得不到首 token。Chunked Prefill、优先级和 token budget 本质上都在处理这个矛盾。

调度器每轮真正决定什么

一个最小调度器不只是“从队列里拿前 N 个请求”。它至少要回答：

  1. 本轮允许处理多少 token？
  2. 哪些请求继续 Decode？
  3. 哪些新请求可以进入 Prefill？
  4. KV Cache 是否还有足够块？
  5. 资源不足时等待、抢占还是重计算？

下面的伪代码只表达控制关系，不代表某个框架的真实实现：

while engine.is_running:
    budget = scheduler.new_token_budget()
    batch = scheduler.select(running, waiting, budget)

    cache_manager.reserve(batch)
    model_output = model_runner.execute(batch)
    tokens = sampler.sample(model_output)

    scheduler.update(batch, tokens)
    streamer.publish(tokens)
    cache_manager.release_finished(batch)

select()、reserve() 和 update() 共同构成了推理引擎的核心控制面。模型 forward 属于数据面，但数据面能否高效运行取决于控制面提供的批次与内存布局。

KV Cache 为什么成为系统核心

自回归生成会反复使用历史 token 的 Key 和 Value。保存它们可以避免每一轮从头计算，但缓存大小会随序列长度和并发数增长。若每个请求预留一整块连续最大长度空间，会产生严重的内部碎片；若缓存块不能灵活回收，又会降低并发能力。

分页 KV Cache 把逻辑连续的序列映射到一组物理块，使系统能按需分配和回收。它带来的不只是“省显存”，还改变了调度器能够安全接纳多少请求，以及前缀共享、抢占和多分支生成的实现方式。

常见误区与失败模式

吞吐高不等于体验好

增大批次通常能提高总 token 吞吐，但可能恶化 TTFT 或 TPOT。服务评测至少要同时报告吞吐、首 token 延迟、逐 token 延迟和尾延迟。

GPU 利用率高不等于系统健康

GPU 长时间忙碌可能是有效计算，也可能是长 Prefill 阻塞、无效 padding 或不合理重计算。必须结合请求队列和缓存状态解释利用率。

能生成正确文本不等于调度正确

并发场景还需要验证取消请求、超时、资源释放、停止条件和流式顺序。单请求输出对拍无法覆盖这些系统问题。

如何验证一个最小推理框架

可以按四层证据逐步验收：

  1. 正确性：单请求输出与参考实现对齐。
  2. 状态机：并发、取消、完成和资源释放不破坏状态。
  3. 资源：KV block 的分配、引用和回收可追踪，无泄漏。
  4. 服务指标：固定请求集合下记录 TTFT、TPOT、吞吐和峰值显存。

本篇是原理与源码阅读导图，没有给出特定 GPU 的实测 benchmark。后续文章会分别拆解 PagedAttention、Continuous Batching 和 Chunked Prefill，并映射到 mini-infer 的具体模块。

Prefix Cache 与 RadixAttention：复用前缀不只是做哈希

比较块哈希缓存和 radix tree 前缀缓存，说明命中、引用、驱逐和 cache-aware scheduling 的系统联系。

2026-07-31约 2 分钟进阶
Prefix CacheRadixAttentionSGLang

问题背景

系统提示词、长文档模板和多轮会话经常重复。若每个请求都重新 Prefill，相同前缀会重复消耗计算。前缀缓存保存已经计算的 KV，并在新请求到达时复用最长匹配部分。

一句话结论

块哈希缓存适合用固定 block 表达和查找共享前缀；radix tree 能表达任意粒度的公共路径。真正困难的不是“找到命中”，而是让匹配、引用计数、驱逐和调度保持一致。

两种表示

Block hash:
  hash(tokens[0:16]) -> physical block 7

Radix tree:
  system prompt
      ├── user A history
      └── user B history

哈希方案通常按完整块复用，数据结构简单，并与 Paged KV 自然结合。Radix tree 可以在共享路径上分叉，更适合复杂前缀集合，但树的拆分、合并和驱逐更复杂。

缓存键必须包含什么

仅使用 token IDs 可能不够。模型版本、adapter、位置编码条件、图像特征或影响 KV 的配置变化都可能使缓存失效。缓存键漏掉条件会产生“命中但输出错误”的危险问题。

调度为何要感知缓存

如果队列中两个请求分别命中 10% 和 90% 的前缀，优先处理高命中请求可能减少 Prefill 工作量、提高吞吐；但长期只追求命中率会伤害公平性。Cache-aware scheduling 必须在复用收益、等待时间和优先级之间取舍。

驱逐与引用

正在被运行请求引用的节点不能驱逐；空闲节点可以按 LRU 或成本策略回收。前缀树节点和物理 KV block 的生命周期必须同步，否则会出现悬空映射或泄漏。

验收清单

  1. 相同前缀命中后，输出与无缓存路径一致。
  2. 只差一个 token 的请求在正确位置分叉。
  3. 不同模型或 adapter 不发生错误共享。
  4. 驱逐后物理块计数恢复。
  5. 命中率提升同时报告公平性和尾延迟。

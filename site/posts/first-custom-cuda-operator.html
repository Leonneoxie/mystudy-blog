先说结论：kernel 能输出，只完成了 20%

第一个 CUDA kernel 往往只有十几行，但真正困难的不是 __global__ 语法。一个可以进入模型或算子库的实现，至少要同时回答五个问题：

  1. 数学契约：计算结果是什么，允许多大误差？
  2. 接口契约：支持哪些 shape、dtype、device、layout 和 stream？
  3. 执行映射：元素如何映射到线程，访存是否连续，边界是否安全？
  4. 性能证据：和谁比较，如何计时，瓶颈来自计算、带宽还是启动开销？
  5. 可复现证据：源码、环境、命令和原始结果能否让别人重跑？

本文用向量加法建立这套闭环。它不是为了重新发明 torch.add，而是因为它几乎没有数学噪声：一旦结果或性能异常，问题通常就在线程映射、接口包装、计时方法或访存模式里。

1. 先写契约，再写 kernel

设 x、y 为长度相同的一维 CUDA tensor：

$$out_i = x_i + y_i,\quad 0 \le i < n$$

第一版刻意收紧边界：只支持 CUDA、FP32、连续内存、相同 shape，不做广播。没有实现的能力应明确拒绝，不能让它在部分输入上“碰巧能跑”。

维度V1 教学实现的约定不满足时
device同一块 CUDA GPU明确报错
dtypeFP32明确报错
shape完全相同，不广播明确报错
layoutcontiguous拒绝或由包装层显式转换
streamPyTorch 当前 CUDA stream异步执行，不擅自同步

2. 从线程层级理解 grid-stride loop

CUDA 的执行结构是 Grid → Block → Thread。线程不会自动知道自己负责哪个元素，索引映射必须由 kernel 明确给出。

下面的 grid-stride loop 可以覆盖任意长度：

__global__ void add_kernel(
    const float* x, const float* y, float* out, int64_t n) {
  for (int64_t i = blockIdx.x * blockDim.x + threadIdx.x;
       i < n;
       i += blockDim.x * gridDim.x) {
    out[i] = x[i] + y[i];
  }
}

第一次循环中，全局线程编号是 blockIdx.x * blockDim.x + threadIdx.x；数据更长时，线程以整个网格的线程总数继续前进。这样 n 不必是 block size 的整数倍，网格大小也能与数据规模解耦。索引使用 int64_t，避免大 tensor 在 32 位索引上溢出。

3. 合并访存决定带宽利用率

向量加法每个 FP32 元素只做一次加法，却至少读取 x/y 并写回 out，即约 12 B/element。算术强度约为 1 FLOP / 12 B，所以它通常受显存带宽限制，而不是计算限制。

相邻线程访问相邻地址，硬件才容易把一个 warp 的请求合并成较少的内存事务。这也解释了为什么非连续切片不能随意传入：代码按扁平连续数组解释输入，stride 语义已经丢失。包装层可以调用 contiguous()，但复制成本必须计入端到端 benchmark。

4. PyTorch 包装层不是胶水代码

实际扩展还需要输入检查、设备保护、输出分配和 kernel launch：

torch::Tensor add_cuda(torch::Tensor x, torch::Tensor y) {
  TORCH_CHECK(x.is_cuda() && y.is_cuda(), "inputs must be CUDA tensors");
  TORCH_CHECK(x.scalar_type() == torch::kFloat32, "only FP32 is supported");
  TORCH_CHECK(y.scalar_type() == x.scalar_type(), "dtype mismatch");
  TORCH_CHECK(x.sizes() == y.sizes(), "shape mismatch");
  TORCH_CHECK(x.is_contiguous() && y.is_contiguous(), "contiguous required");

  at::cuda::CUDAGuard guard(x.device());
  auto out = torch::empty_like(x);
  const int64_t n = x.numel();
  if (n == 0) return out;

  constexpr int threads = 256;
  const int blocks = static_cast<int>(
      std::min<int64_t>((n + threads - 1) / threads, 4096));
  cudaStream_t stream = at::cuda::getCurrentCUDAStream();
  add_kernel<<<blocks, threads, 0, stream>>>(
      x.data_ptr<float>(), y.data_ptr<float>(), out.data_ptr<float>(), n);
  C10_CUDA_KERNEL_LAUNCH_CHECK();
  return out;
}

这里的工程要点是：CUDAGuard 保证多 GPU 时使用输入所在设备；当前 stream 保持 PyTorch 的异步语义；空 tensor 不发射 kernel；launch check 尽早暴露配置错误。算子内部不应调用 cudaDeviceSynchronize()，否则会破坏并发并掩盖 stream 问题。

5. 正确性：不只跑一次 allclose

最小 shape 矩阵应包含：

  • n=0、1、31、32、33 等边界；
  • 非 block size 整数倍；
  • 大张量；
  • 不同 dtype（如果声明支持）；
  • 非连续张量：明确拒绝或正确处理；
  • 多 stream 场景；
  • 与 torch.add 的容差对拍。
SIZES = [0, 1, 31, 32, 33, 255, 256, 257, 4096, 1_000_003]
for n in SIZES:
    x = torch.randn(n, device="cuda", dtype=torch.float32)
    y = torch.randn_like(x)
    torch.testing.assert_close(ext.add(x, y), x + y,
                               rtol=1e-5, atol=1e-6)

31/32/33 检查 warp 边界，255/256/257 检查 block 边界，质数规模检查尾部。还要验证 CPU tensor、dtype/shape 不一致和非连续输入会按契约报错。错误路径也是接口质量的一部分。

6. 性能：先保证计时可信

GPU launch 是异步的，直接用 Python 时钟通常只测到提交时间。正确做法是预热并使用同一 stream 上的 CUDA Event：

def bench(fn, warmup=50, iters=200):
    for _ in range(warmup):
        fn()
    start = torch.cuda.Event(enable_timing=True)
    end = torch.cuda.Event(enable_timing=True)
    start.record()
    for _ in range(iters):
        fn()
    end.record()
    end.synchronize()
    return start.elapsed_time(end) / iters

每组数据至少报告 GPU、PyTorch/CUDA 版本、dtype、元素数、warmup/iters 和 baseline。FP32 的有效带宽口径为：

effective_gbps = (12 * n) / (latency_ms * 1e-3) / 1e9
规模常见主导因素应如何解读
很小Python、dispatcher、kernel launch自定义实现更慢很正常
中等launch 与内存吞吐共同影响扫描 shape，观察拐点
很大显存带宽比较有效带宽，不只看 FLOPS

7. Nsight 应该回答什么

CUDA Event 证明“慢”之后，再用 Nsight Systems 看时间线、用 Nsight Compute 分析单个 kernel：

nsys profile -t cuda,nvtx,osrt -o reports/vector_add python bench_vector_add.py
ncu --set full -o reports/vector_add_kernel python bench_vector_add.py

对向量加法应检查 kernel 是否被大量细碎 launch 淹没、load/store 是否连续、有效带宽是否随规模上升、是否出现意外同步，以及 occupancy 是否被异常的 block 配置限制。如果小输入耗时几乎不随 n 变化，通常是 launch overhead；大输入带宽仍很低，才继续检查访存和对齐。

8. baseline 到优化版：每一步都保留

版本核心特性学习目标可能收益
B0torch.add建立框架基线真实参照
V1标量 grid-stride跑通索引、扩展与 stream建立闭环
V2float4 + 尾部处理学习对齐与宽访存取决于 shape/对齐
V3与后续逐元素操作融合减少中间张量和 launch通常更有工程价值

V2 不保证击败高度优化的 torch.add。单次加法的优化空间有限，真正有价值的方向往往是 V3，例如融合 bias + residual + activation，减少全局内存往返。一次“没有更快”的实验仍然成功，只要测量可信，而且数据证明瓶颈确实是 launch 或带宽。

多 GPU 设备错误缺少 device guard在非默认 GPU 测试，使用 CUDAGuard
自定义 stream 偶发错误硬编码默认 stream加 stream 测试，取得当前 stream

一个可交付实验至少留下：环境与编译命令、B0/V1/V2/V3 源码、正确性原始输出、各 shape 延迟与有效带宽、profiler 报告，以及失败样例和适用边界。

11. 学完后的验收标准

  • 能解释 Grid、Block、Warp、Thread 与元素索引的关系；
  • 能写出支持任意 n 的 grid-stride loop；
  • 能正确处理 device、dtype、layout 和 stream；
  • 能设计边界 shape 与错误路径测试；
  • 能用 CUDA Event 构建可信 benchmark；
  • 能判断向量加法为何受带宽限制；
  • 能用 Nsight 区分 launch、访存和同步问题；
  • 能保留 baseline 与优化阶梯，并接受“该优化不适合此场景”的结论。

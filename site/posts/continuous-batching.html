Continuous Batching 为什么比静态批处理更适合在线生成

用请求完成时间不同这一事实，解释连续批处理如何在每个解码步重新组织批次，并讨论吞吐与延迟边界。

2026-07-29约 2 分钟进阶
Continuous BatchingSchedulingThroughput

问题背景

静态批处理要求一批请求一起开始、一起结束。文本生成长度不一致，短请求完成后仍要等待最长请求，空出的计算位置无法及时交给新请求。在线服务还会持续收到请求，更不适合固定批次边界。

一句话结论

Continuous Batching 在每轮迭代后移除已完成请求并接纳新请求，让批次成为动态状态，而不是一次性张量。

调度循环

while waiting or running:
    running = [req for req in running if not req.finished]
    while waiting and token_budget.can_admit(waiting[0]):
        running.append(waiting.pop(0))
    outputs = decode_step(running)
    update_requests(running, outputs)

这段代码是控制流模拟。生产实现还需管理 Prefill token、KV block、取消、优先级和分布式 worker 一致性。

为什么吞吐会上升

假设一批四个请求分别生成 2、4、8、16 个 token。静态批处理在 16 轮内都占用四个槽位，其中大量位置只是 padding。连续批处理能在第 2、4、8 轮释放槽位并接入新请求，使有效 token 比例提高。

但“始终塞满 GPU”不是唯一目标。调度器还必须限制：

  • 单轮总 token 数；
  • Prefill 与 Decode 的资源比例；
  • 最大并发序列和 KV Cache 使用；
  • 高优先级请求的等待时间；
  • 长请求对短请求的影响。

三种容易混淆的指标

  • 吞吐：单位时间完成多少 token 或请求。
  • TTFT：请求进入到首 token 返回的时间。
  • TPOT：生成阶段相邻 token 的平均时间。

提高并发通常能提升吞吐，但排队和批次变大可能恶化 TTFT、TPOT 或尾延迟。因此 benchmark 必须给出请求到达模型和输出长度分布，不能只报告离线 tokens/s。

常见失败

已完成请求没有立即释放 KV

调度列表看似移除了请求，但缓存仍被引用，运行一段时间后出现伪 OOM。

随机数状态随批次位置变化

请求进入和离开导致批次重排，若采样 RNG 绑定 batch index，同一请求在不同并发下可能得到不同输出。每请求 seed 应绑定请求身份。

取消只断开网络连接

如果调度器和 KV 管理器没有收到取消事件，GPU 仍会为无人接收的请求生成 token。

最小验收

构造固定到达时间和输出长度的请求流，对比静态与连续批处理的有效槽位比例；随后检查每个请求输出、seed 稳定性和最终空闲块数量。该模拟能验证调度状态机，但不能替代 GPU 性能结论。

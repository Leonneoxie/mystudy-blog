FlashAttention 为什么不是“更快的 Softmax”

从 IO 复杂度、online softmax 递推和分块累积三个层面，解释 FlashAttention 如何在不物化完整注意力矩阵的前提下保持数学等价。

先给结论

FlashAttention 的核心不是重新发明 softmax，而是改变注意力计算的数据移动方式：把 $QK^T$、softmax 和 $PV$ 融合在同一分块流水中，让中间注意力矩阵尽量停留在片上存储，而不是往返显存。

它必须同时满足两件事：

  1. 分块后的输出与标准 attention 数学等价；
  2. HBM 读写量显著降低，节省的 IO 足以覆盖额外递推计算。

只实现一个 online softmax 函数，并不能自动得到 FlashAttention。

标准 Attention 的问题发生在哪里

标准形式为：

$$ S = QK^T / \sqrt{d}, \qquad P = \operatorname{softmax}(S), \qquad O = PV $$

当序列长度为 $N$ 时，$S$ 和 $P$ 都是 $N \times N$。朴素实现通常经历：

Q, K 读取
  → 写出完整 S
  → 读取 S 做 softmax
  → 写出完整 P
  → 读取 P、V 做矩阵乘

计算量依旧是 $O(N^2d)$，但显存流量和 $N^2$ 中间张量会快速成为瓶颈。GPU 的算力增长通常快于显存带宽增长，因此“少搬数据”可能比“少做几次标量运算”更重要。

Online Softmax 如何支持分块

对一行 logits $x$，稳定 softmax 使用：

$$ m = \max_i x_i,\qquad \ell = \sum_i e^{x_i-m},\qquad y_i = e^{x_i-m}/\ell $$

如果 logits 分成旧块和新块，可以递推维护行最大值与归一化和：

$$ m_{\text{new}} = \max(m_{\text{old}}, m_{\text{block}}) $$

$$ \ell_{\text{new}} = e^{m_{\text{old}}-m_{\text{new}}}\ell_{\text{old}}

  • e^{m_{\text{block}}-m_{\text{new}}}\ell_{\text{block}}

$$

旧输出累积量也必须乘以 $e^{m_{\text{old}}-m_{\text{new}}}$ 重新缩放。这个步骤经常被初学实现漏掉：最大值变化后，旧块与新块必须重新落到同一指数基准。

分块前向的状态机

对一个 Q tile，遍历所有 K/V tile：

m_i = -inf
l_i = 0
acc = 0

for k_tile, v_tile in kv_tiles:
    scores = q_tile @ k_tile.T * scale
    block_max = scores.max(dim=-1)
    new_max = maximum(m_i, block_max)

    old_factor = exp(m_i - new_max)
    probs = exp(scores - new_max[:, None])

    acc = acc * old_factor[:, None] + probs @ v_tile
    l_i = l_i * old_factor + probs.sum(dim=-1)
    m_i = new_max

output = acc / l_i[:, None]

这段伪代码最重要的不是语法，而是三个跨 tile 状态：

  • m_i：当前已经见过的最大值；
  • l_i：相对于 m_i 的指数和；
  • acc：同一缩放基准下的输出累积。

因果 Mask 应该放在哪里

因果 mask 必须在 block max 和指数计算之前生效：

未来位置 score = -∞
      ↓
参与 block max
      ↓
参与 exp 与归一化

边界 tile 通常只有一部分位置有效。若先计算 softmax 再把未来位置清零，归一化分母已经错误。

工程实现中还要区分：

  • 完全位于对角线左下方的 tile：无需逐元素 mask；
  • 与对角线相交的 tile：需要细粒度 causal mask；
  • 完全位于未来区域的 tile：可以直接跳过。

为什么 tile 越大不一定越快

tile 选择同时影响：

因素tile 增大后的变化
数据复用通常改善
shared memory占用增加
register pressure增加，可能 spill
occupancy可能下降
边界浪费短序列时更明显
Tensor Core 利用率满足形状约束时改善

因此 tile 大小不能只按矩阵维度猜测。需要结合 shared-memory 预算、寄存器数、warp 数和目标 GPU 做 profile。

正确性验收不能只看一个输出

建议至少保留四级测试：

  1. 小 shape 与 PyTorch SDPA 对拍；
  2. causal/non-causal、奇数长度和非整 tile 边界；
  3. FP32 累积 oracle 与 FP16/BF16 容差；
  4. 长序列压力测试，确认没有 NaN、溢出或 mask 泄漏。

误差报告至少包含：

max_abs_error
mean_abs_error
relative_l2_error
NaN / Inf count

性能验收应该回答什么

不能只报告“比 Python 快”。至少需要比较：

  • PyTorch SDPA；
  • 本地 naive/fused baseline；
  • 优化版本；
  • 不同 batch、head、sequence length、head dimension；
  • warmup 后的 P50/P95 latency；
  • 峰值显存；
  • profiler 中的 HBM 流量、occupancy 和 kernel 时间。

如果只在一个小 shape 上快，或者时间主要花在 launch overhead，它还不能证明算法级收益。

从课程实现中应该学到什么

一个好的 FlashAttention Lab 应保留演进版本：

F0：PyTorch oracle
F1：naive attention
F2：online softmax correctness
F3：tiled fused forward
F4：causal 与边界优化
F5：profile 驱动的 tile/warp 调优

最终版本不是唯一学习资产。每一级新增了什么、修复了什么瓶颈、牺牲了什么资源，才是算子优化教程真正应该留下的内容。

用一个小例子手算 online softmax

假设一行 score 分成 S1=[1,2]、S2=[3,4]。第一块最大值 m1=2，分母 l1=e^-1+1；合并第二块时，新最大值变为 4，旧状态必须重标定：

$$m_2=4,\qquad l_2=e^{m_1-m_2}l_1 + e^{-1}+1$$

输出累积量也要乘同一个因子。遗漏这一步，小随机输入可能看似接近，长序列或大幅值 score 会迅速失真。

实验矩阵与失败诊断

至少扫描 N∈{1,31,32,33,127,128,129,512,2048}、多个 head dimension、causal/non-causal 和 FP16/BF16，并记录 max_abs_error、P50/P95、峰值显存与基线名称。

诊断顺序应是：先用 FP32 小矩阵逐元素比较 score、行最大值、分母和输出；再测极大幅值、全遮蔽行与非整除 tile；正确后才用 CUDA Event、Nsight Systems 和 Nsight Compute 定位性能。RTX A1000 6GB 等设备可以完成算法验证，但小 shape 趋势不能直接外推为数据中心 GPU 的生产结论。

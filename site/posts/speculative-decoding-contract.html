投机解码真正难在接受规则与状态回滚

从 draft、verify、accept 三步解释投机解码，并梳理 KV Cache、采样状态和停止条件的回滚契约。

2026-07-31约 2 分钟高级
Speculative DecodingSamplingKV Rollback

一句话结论

投机解码通过便宜 proposer 一次提出多个 token，再由目标模型并行验证；是否加速取决于接受率和验证成本，而正确性取决于接受规则及所有请求状态能否一致回滚。

三步执行

draft:  提议 d1 d2 d3 d4
verify: 目标模型一次计算这些位置的分布
accept: 接受前缀，遇到拒绝点改由目标分布采样

如果平均每次验证能接受多个 token，目标模型 forward 次数可能减少。但 proposer 太重、接受率太低或 batch 调度不匹配时，投机路径反而更慢。

为什么不能只比较 greedy 输出

Greedy 模式下可直接检查 draft token 是否等于目标模型 argmax；随机采样需要遵循修正后的分布，才能保持与目标分布一致。错误的“匹配就收、不匹配就重采”可能改变总体采样分布。

回滚对象

拒绝发生后，需要一致处理：

  • 已预留但未接受的 KV token；
  • 序列长度和 block table；
  • RNG/采样状态；
  • repetition/frequency penalty 历史；
  • stop string 与结构化解码状态；
  • 流式输出缓冲区。

如果 token 已经发送给客户端，就不能再静默撤回。因此验证应先于外部可见提交。

最小实验设计

使用 n-gram proposer 可以在不加载第二个模型的情况下验证控制流：从请求已有 token 中查找相同后缀并提出后续 token。分别构造高重复文本和随机文本，预期前者接受率更高。这个实验验证机制和退化条件，不代表 draft model 或 EAGLE 的真实收益。

必须报告的指标

  • 平均接受 token 数；
  • 接受率分布，而不只是均值；
  • proposer、verify 和 rollback 时间；
  • 端到端 TPOT 与吞吐；
  • 低接受率 workload 的反例；
  • 开启前后输出分布或确定性对拍。

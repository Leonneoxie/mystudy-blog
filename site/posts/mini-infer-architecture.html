mini-infer 为什么把推理引擎拆成四个边界

复盘教学型推理框架如何划分请求状态、调度、KV Cache 和模型执行，并解释哪些生产能力不应硬塞进主循环。

四个边界组成最小推理引擎

TECH MAP
01Request State
02Scheduler
03KV Manager
04Model Runner
  • 控制面与数据面分离
  • 状态拥有唯一真相源
  • backend 可以独立替换

项目目标

mini-infer 的目标不是成为 vLLM 或 SGLang 的轻量替代品，而是让学习者能沿着一条清晰路径理解现代推理引擎：先跑通自回归循环，再加入分页 KV、连续批处理、缓存、投机解码、量化、分布式和多模态边界。

一句话结论

教学框架最重要的设计不是 feature 数量，而是让请求状态、调度决策、缓存生命周期和模型执行保持可观察、可替换、可单独验证。

四个核心边界

Request / Sequence State
          ↓
      Scheduler  ←→  KV Cache Manager
          ↓                ↓
       Model Runner / Attention Backend

请求状态

请求对象保存 token、生成限制、采样配置、完成原因和每请求随机状态。它不能依赖当前 batch index，否则连续批处理重排后，同一请求的行为会漂移。

调度器

调度器只决定本轮谁运行、处理多少 token，以及资源不足时等待、抢占还是重算。它不应直接实现注意力计算，也不应绕过缓存管理器修改物理块。

KV Cache 管理器

缓存管理器负责 block 分配、引用、共享、回收和回滚。调度器可以询问预算，但物理生命周期必须有唯一真相源，否则取消、投机拒绝和前缀共享很容易产生泄漏。

模型执行器

Model runner 把调度结果整理成张量和 attention metadata，调用 PyTorch、FlashInfer 或其他 backend。Kernel 选择属于执行层；它不能反向决定业务请求是否完成。

为什么不能把所有前沿能力塞进一个 Engine.step

结构化输出可以约束采样状态，LoRA 会影响权重和缓存键，P/D 分离需要跨 worker 传递 KV，全模态生成甚至包含 diffusion 和 codec。若这些能力都通过条件分支堆进主循环，教学主线会迅速失去边界。

mini-infer 的取舍是：文本推理通用机制进入主线；VLM encoder/projector 作为边界扩展；完整图像、音频和视频生成保留为独立 omni pipeline 课程。未覆盖不等于缺陷，而是明确产品范围。

如何验收架构而不只是输出

  1. 调度器测试不加载真实模型，也能复现请求状态转换。
  2. KV 管理测试能在完成、取消和回滚后恢复全部块。
  3. Model runner 能替换 reference backend 与真实 kernel backend。
  4. 固定请求 trace 可以重放，比较输出和调度事件。
  5. benchmark 同时记录 TTFT、TPOT、吞吐、显存和失败条件。

这些测试分别建立控制面、资源面和数据面的证据。只有单请求文本正确，不能证明它已经是可靠的推理系统。

当前边界

mini-infer 已覆盖核心机制和若干真实 backend 教学入口，但生产级容错、大规模 MoE/EP、完整 P/D 基础设施与 Omni 异构流水仍应按“概念、原型、真实后端、性能验证”四级标注，不能用同名 feature 混淆完成度。

延伸学习

建议按 L01 → L02 → L03 → L04 阅读：先建立执行循环，再理解 Paged KV、Continuous Batching 和缓存/抢占。完成后再进入投机解码、真实 kernel、量化和分布式章节。

接口应表达状态，而不是泄漏实现

class Scheduler:
    def schedule(self, waiting, running, budget) -> BatchPlan: ...

class KVCacheManager:
    def reserve(self, request_id, tokens) -> SlotMapping: ...
    def release(self, request_id) -> None: ...

class ModelExecutor:
    def execute(self, plan: BatchPlan, slots: SlotMapping) -> ModelOutput: ...

BatchPlan 和 SlotMapping 是边界契约：调度器不应直接修改 CUDA tensor，执行器也不应偷偷决定公平性。这样才能分别用纯 CPU 状态机、mock executor 和真实 GPU 做分层测试。

架构验收矩阵

测试层替身证明什么
请求状态无 GPU状态迁移、停止与取消
调度器假 KV 容量预算、公平性、抢占
KV 管理器小内存池分配守恒、引用与释放
执行器固定 logitsbatch/slot 映射
端到端小模型token 与框架 oracle 一致

生产能力应通过 adapter 或独立策略逐步接入。把 prefix cache、投机解码、P/D 分离全部堆进 Engine.step，会让状态回滚和测试组合呈指数增长。

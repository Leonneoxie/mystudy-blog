vLLM、SGLang 与 vLLM-Omni 应该如何比较

先说结论

三个项目不能只用同一张功能勾选表排名。vLLM 面向广覆盖的模型服务运行时，SGLang 强调前缀复用、调度和大规模服务能力，vLLM-Omni 则把问题扩展到文本、图像、音频、视频等异构阶段流水线。选型应从 workload 和运维边界出发。

不应怎样选

只数 feature

同名特性可能处于不同完成度：文档概念、原型、真实后端和有 workload 的性能验证不是同一层。

用单个 tokens/s 决定

模型、输入输出长度、并发、硬件、量化格式和延迟 SLO 改变后，排序可能变化。必须使用自己的请求分布。

把 Omni 当作“多一个图片输入”

生成图像、音频或视频可能包含自回归 Transformer、codec 和 diffusion 等不同循环。它们需要阶段级并行、资源分配和流式输出，而不是在文本引擎上加一个字段。

mini-infer 应该学什么

mini-infer 不应追求复制所有生产 feature。更有教学价值的是建立四级证据：概念解释、最小原型、真实 backend、性能验证。Paged KV、连续批处理、chunked prefill 和前缀缓存进入主线；大规模 MoE/EP 和完整 Omni pipeline 保持边界说明或独立课程。

选型清单

  1. 明确模型与任务：文本、VLM、embedding 还是生成媒体。
  2. 固定请求到达和长度分布。
  3. 明确 TTFT、TPOT、吞吐和尾延迟目标。
  4. 核对硬件、量化与 kernel 组合。
  5. 验证观测、故障恢复和发布能力。

框架迭代很快，本篇只对核验日期负责，部署前必须重新检查 stable 文档与 release notes。

用同一份 workload 做决策

框架比较必须固定模型、权重精度、GPU、并发到达轨迹、prompt/output 长度分布和采样参数。推荐至少保留三类 workload：离线吞吐、在线稳态和突发流量。

指标回答的问题常见误用
TTFT P95用户多久看到首 token只报平均值
TPOT P95流式输出是否平稳与 TTFT 混成总延迟
goodput满足 SLO 的有效吞吐只看最大 tokens/s
KV 利用率长上下文容量如何只看模型权重显存
故障恢复worker 异常影响多大单机 happy path 代替

选型结论应带条件

一个合格结论应写成：“在模型 X、GPU Y、长度分布 Z、TTFT/TPOT SLO 下，框架 A 的 goodput 更高，代价是某能力或运维复杂度。”框架版本和 feature 演进很快，因此本文提供的是比较方法，不把任何静态排名包装成永久事实。

多模态框架还要分别记录预处理、encoder、LLM prefill/decode 和跨阶段数据传输；把它们合成一个 tokens/s 会隐藏真正瓶颈。

Prefill 与 Decode 为什么会争抢同一块 GPU

从计算密度和 KV 读取差异出发，理解 chunked prefill、token budget 与 P/D 分离分别解决什么问题。

2026-07-30约 2 分钟进阶
PrefillDecodeChunked Prefill

一句话结论

Prefill 偏计算密集，Decode 偏 KV Cache 读取和小批次调度；把它们直接混在一个无限制队列里，会让长提示词和在线生成互相干扰。

两类工作负载

Prefill 对整段 prompt 建立 KV Cache，输入 token 多，矩阵乘法形状较大。Decode 每轮为每个序列增加少量 token，但反复读取历史 KV。两者对算力、带宽和延迟的需求不同。

长 Prompt 进入
  ├─ 一次完成 Prefill：TTFT 可能较好，但正在 Decode 的请求出现抖动
  └─ 切成多个 Chunk：Decode 更平滑，但新请求首 token 可能推迟

Chunked Prefill 的作用

Chunked Prefill 把长 prompt 分成多个 token chunk，让调度器在 chunk 之间插入 Decode。它不是免费的：chunk 太小会增加调度和 kernel 启动开销，太大又无法缓解阻塞。

因此需要统一 token budget，例如每轮允许 2048 个 token，由 Decode token 和 Prefill chunk 共同消费。策略必须明确是否优先保护正在流式输出的请求。

P/D 分离不是同一个层次

Chunked Prefill 在同一执行资源上进行时间切片；Prefill/Decode disaggregation 则把两个阶段放到不同 worker 或资源池，再传输 KV Cache。后者能独立扩缩容和隔离干扰，但增加 KV 传输、路由、故障恢复和可观测性成本。

只有当计算隔离收益大于传输与运维成本时，P/D 分离才值得。教学框架可先实现双引擎原型和 KV connector 契约，不应把进程间模拟宣称为生产级分离。

应该记录什么

  • prompt 长度和输出长度分布；
  • TTFT、TPOT、吞吐及 P95/P99；
  • 每轮 Prefill/Decode token 数；
  • KV 传输字节和等待时间；
  • chunk 大小变化带来的反例。

本篇是原理与调度契约说明，没有给出特定 GPU 的实测结论。

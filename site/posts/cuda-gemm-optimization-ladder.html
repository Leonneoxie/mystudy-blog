为什么 GEMM 适合学习优化

GEMM 公式很简单：

$$ C_{M\times N}=A_{M\times K}B_{K\times N} $$

但它同时暴露了 GPU 优化的核心矛盾：全局内存带宽、数据复用、线程映射、寄存器压力、occupancy、指令吞吐和硬件矩阵单元。几乎所有深度学习算子优化都能在 GEMM 中找到对应概念。

真正有效的学习方式不是直接阅读最终 Tensor Core kernel，而是保留一条可测量的演进阶梯。

G0：先建立可信基线

基线包含两个对象：

  • 正确性 oracle：torch.matmul 或 cuBLAS；
  • 最小 CUDA kernel：每个线程计算一个 $C_{ij}$。
float acc = 0.0f;
for (int k = 0; k < K; ++k) {
    acc += A[row * K + k] * B[k * N + col];
}
C[row * N + col] = acc;

这个版本通常很慢，因为同一行 A 和同一列 B 被不同线程反复从全局内存读取。但它必须保留，因为后续每一级都需要回答“相对哪个 baseline 提升”。

基线报告应固定：

shape / dtype / layout
warmup / repeat
latency P50 / P95
TFLOPS
max error
GPU / CUDA / compiler

G1：Shared Memory Tiling

将 A、B 切成 tile，由一个 thread block 协同加载：

Global A tile ─┐
               ├→ Shared Memory → 多次复用 → C tile
Global B tile ─┘

若 tile 边长为 $T$，理想情况下一个 tile 的数据会被约 $T$ 个线程复用，从而降低全局内存读取。

关键正确性点：

  1. 每轮加载后 __syncthreads()；
  2. 使用完成后再次同步，才能覆盖 shared memory；
  3. M/N/K 非 tile 整数倍时做边界保护；
  4. 越界填零不能污染有效累积。

G2：Register Tiling

一个线程只计算一个输出，通常无法充分复用寄存器中的 A/B 值。Register tiling 让一个线程计算一个小输出块：

thread
├── C00 C01 C02 C03
├── C10 C11 C12 C13
└── register accumulators

同一个 A fragment 可以更新多个 N 方向输出，同一个 B fragment 可以更新多个 M 方向输出。

代价是寄存器数量快速上升。超过阈值后会发生：

  • occupancy 下降；
  • local-memory spill；
  • 更多依赖链；
  • 编译器调度压力。

所以 register tile 不是越大越好。

G3：合并访存和向量化

Shared tiling 解决“重复读取”，但不自动保证“读取方式高效”。还需要检查：

  • warp 内线程地址是否连续；
  • 是否满足 16-byte 对齐；
  • 能否使用 float4、half2 等向量访问；
  • B 的布局是否导致跨步读取；
  • shared-memory bank conflict 是否出现。

向量化前必须证明：

指针对齐
维度满足向量宽度
边界路径安全

否则性能优化会变成未定义行为。

G4：双缓冲与异步拷贝

单缓冲流水是：

load tile → wait → compute tile → load next tile

双缓冲希望形成：

compute tile n
     ∥
load tile n+1

Ampere 及之后架构可以利用异步 global-to-shared copy，但只有计算量足够、同步和 buffer 切换正确时才有收益。小矩阵可能被额外控制开销抵消。

G5：Tensor Core

Tensor Core 不是把标量乘加换个函数名。需要同时满足：

  • 支持的 dtype；
  • MMA fragment 形状；
  • layout 与对齐；
  • 累积精度；
  • warp 级线程协作；
  • K 维 padding；
  • epilogue 的输出转换。

性能比较必须包含 cuBLAS。自定义 kernel 超过 naive 很容易，接近成熟库才说明实现真正利用了硬件。

用 Roofline 决定下一步

算术强度：

$$ I = \frac{\text{FLOPs}}{\text{Bytes transferred}} $$

Roofline 给出近似上限：

$$ P \le \min(P_{\text{peak}}, I \cdot BW_{\text{peak}}) $$

如果 kernel 处于带宽区，应优先减少访存、改善合并访问和复用；如果已经进入计算区，再关注指令吞吐、Tensor Core 和流水并行。

这比“看到 shared memory 就加 shared memory”更可靠。

一组可复现的实验矩阵

不要只测方阵。LLM 中的 GEMM 经常是 M 很小、K/N 很大的矩形：

场景示例 shape (M,N,K)代表含义首要观察
方阵教学(1024,1024,1024)验证 tiling吞吐、占用率
Prefill(2048,4096,4096)多 token 投影Tensor Core、带宽
Decode(1,4096,4096)单 token GEMV 化launch、权重读取
小批 Decode(16,4096,4096)continuous batchingbatch 拐点
非整除边界(257,769,513)尾块与 mask正确性、分支

每个版本先通过 torch.testing.assert_close，再固定 warmup、iters 和时钟条件计时。结果表应同时保存毫秒、TFLOPS、相对 G0 加速比和 cuBLAS 比值，避免“只比自己的慢 baseline 快很多”。

优化决策示例

Global Load Efficiency 低  → 改线程到地址的映射
Shared Memory 冲突明显    → 处理 bank conflict / padding
Occupancy 低且寄存器过多  → 缩小 register tile
访存已好但流水有气泡      → 双缓冲或异步拷贝
SIMT 接近上限             → 评估 WMMA / MMA / CUTLASS
Decode 的 M≈1             → 改看 GEMV 路径，不硬套方阵 kernel

Profiler 证据应决定下一步。若没有观察到对应瓶颈，就不应仅因为某个技巧“更高级”而加入代码。生产选择仍要比较 cuBLAS、cuBLASLt 或 CUTLASS；手写实现未超过库并不等于实验失败，只要报告能够解释差距。
